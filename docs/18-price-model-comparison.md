# 18 · 双电价模型对比与组合方案（July MQ-RNN × 林 LightGBM）

> 背景：2026-10-21 July 与林各自上传了一个电价预测模型，要求评估"哪个好、怎么组合"。
> 当前状态：电价同协议对决已完成；AMPDNet 的 P0-A 独立 rolling-origin 也已完成，正式 P0-P4 结果见 [`reports/official_experiment/official_experiment_report.md`](../reports/official_experiment/official_experiment_report.md)。本文保留模型组合决策和后续待排期项，不替代正式主实验报告。
> 本文档是评估结论与落地决策。**2026-10-22 更新：同协议对决已执行（§5），
> §1/§4 的初步结论已按对决结果修正——以修正后为准。**

> 2026-10-25 提交口径：总结材料统一引用 §5.1 同协议表；§2 的 9.24 / +29.1%
> 是历史环境结果。保形校准已完成（PR #8），结果另见 docs/15 §7.1，不能把校准实验
> 的 0.756 覆盖率替换进 §5.1 的未校准对决表。

## 1. 结论先行（对决后修正版）

1. **同协议对决已跑完**（§5）：林的 LightGBM 是明确胜者
   （MAE 9.52 / skill +26.9% / 峰值命中 0.75）；July 的 MQ-RNN 移植版
   skill −9.2%，未过"跑赢昨日延续"的生产臂门槛。
2. **泄漏检查**：July 的模型按绝对时间切分（训练截止 2013-01-26、验证截止
   2013-07-07，测试点全部在其后），无泄漏；林的协议逐任务日滚动重训也干净。
   **但对决中发现林的基准脚本里 MQ-CNN 臂存在训练泄漏**（全序列训练），
   修正后 MQ-CNN 真实水平 skill −125.5%，docs/15 旧数字（+17.3%）作废。
3. **生产骨干维持林的 LightGBM 不变**——对决结果加强了这一决策。
4. **MQ-RNN 的出路明确**：分任务明细显示它输在拿不到日前负荷预报
   （calendar-only 口径），热浪尖峰系统性低估；07-20 尖峰日它全场最佳，
   说明序列建模有真实价值。补负荷协变量 → 重跑对决 → 达标再注册为第二臂。
5. **区间校准优势未复现**：July 自评协议的 PICP80 81.4% 在同协议对决中为
   68.9%，与 LightGBM 的 67.5% 基本相当；两侧 80% 区间都偏窄，
   LightGBM 的 conformal 校准已完成（PR #8），独立严格滚动实验 PICP80
   0.642 → 0.756；站点训练与推理已接通（docs/15 §7.1）。MQ-RNN 校准仍待验证。

## 2. 两个模型的身份卡

| | 林 · LightGBM 分位数 | July · MQ-RNN |
|---|---|---|
| 位置 | 主线 `backend/app/domain/forecast/price_model.py`（PR#5 已合并） | `product/` 旧树 `price_mqrnn.py`（feat/product-mvp-impl 分支） |
| 论文谱系 | 梯度提升树 + 分位数损失 | arXiv:1711.11053 MQ-RNN 的独立复现改（forking-sequences、共享解码器、截断 BPTT，论文级忠实） |
| 数据集 | GEFCom2014-P（真实市场 LMP） | 同 |
| 协议 | 15 个竞赛任务日 × 24h = 360 点，**逐日滚动重训**，日前 24h | 39 个连续 96h 窗口 = 3744 点，**单次训练**（20 轮，验证集选第 17 轮），96h 长时域 |
| MAE | 9.24（基准 naive_daily 13.03） | 8.74（基准 seasonal_day 10.95） |
| skill | +29.1% | +20.2% |
| 80% 区间覆盖率 | **68.6%（偏窄，低估尾部）** | **81.4%（≈名义 80%，校准优秀）** |
| 峰值命中率 | 0.75 | 未评（该指标在其协议下未定义） |
| 工程状态 | 注册表算法臂、降级链、前端、17 项测试，**已在生产链路** | 工件 + manifest + 3745 行逐点预测存档齐全，但单位/时区与线上不符，作者自标"未安装为生产模型"；代码在废弃 product/ 树 |
| 自检诚实度 | 明确记录"MQ-CNN 没赢，不修饰" | manifest 自标"calendar-only adaptation，非竞赛分数复现，未做中国站点验证" |

两个模型的测试期有 9 个任务日重叠（07-13~07-25、12-07、12-08），具备做
**逐点对决**的数据基础（见 §5）。

一个需要双方都正视的事实：July 的测试存档显示 2013-12-13/14 实际电价冲到
134.81/80.08，MQ-RNN 的 P50 只给到 43.5/38.8——**12 月尖峰被系统性低估**。
林的文档同样指出任务日集中在 6–7 月与 12 月的厚尾时段是区间偏窄的主因。
这不是谁的模型差，是电价这个对象的固有难点：极端价格由稀缺性与市场博弈驱动，
纯历史外推都抓不全。对储能套利的影响：错过最贵的放电窗口比买贵一点电损失大得多。

## 3. 为什么不能直接比 MAE

| 差异 | 影响 |
|---|---|
| 测试点数 360 vs 3744 | 林的任务日是竞赛方挑的"难题日"（6-7 月、12 月厚尾），July 的窗口含大量普通日；难题日 MAE 天然偏高 |
| 时域 24h vs 96h | 误差随提前量增长，96h 平均 MAE 与 24h MAE 不是一个量 |
| 逐日重训 vs 单训 | 林每个任务日都用到前一天的数据；July 的模型从没见过 2013-01-26 之后的任何数据，对 12 月测试点等于"用一年前的知识考年底的试" |
| 基准不同 | naive_daily 与 seasonal_day 口径相近但不保证逐点一致 |

结论：skill +29.1% vs +20.2% 的差距里，协议差异的贡献未知，不能归因于模型强弱。

## 4. 组合方案（落地决策）

### 4.1 生产链路（现在）

- 骨干不变：`price_lgbm_quantile`（林）为注册表默认算法臂，降级链、封存对账照旧。
- 区间策略：LightGBM 的保形校准与覆盖率监控已接通（docs/15 §7.1–7.2）；
  老工件需重训才启用校准。严格滚动 PICP80 为 0.756，仍未达名义 0.80，
  调度器风险挡位继续按实测覆盖率保守解释。

### 4.2 MQ-RNN 的接入定位（已部分执行，门槛见 §5.3）

July 的模型要进系统，不是复制文件，而是**按注册表契约重做接入**：

1. ~~从 `product/` 旧树移植 `price_mqrnn.py` 到主线~~ —— **已完成（2026-10-22）**：
   主线 `backend/app/domain/forecast/price_mqrnn.py`，注册表已登记 `price_mqrnn`
   （离线对照臂，product_key=None 不对产品开放），7 项测试含防泄漏红线；
2. **补日前负荷协变量后重跑对决**（§5.3），skill 转正且峰值命中 ≥ 0.5 才推进；
3. **用本站真实现货数据逐站重训**——GEFCom 工件单位是源市场 $/MWh、时区 UTC、
   小时级，与线上 CNY/kWh、Asia/Shanghai、15 分钟不匹配，不可直接上线
   （其 manifest 已自标此限制）；
4. 达标后注册为可选算法臂，与 `price_lgbm_quantile` 并存，
   由封存对账积累本站实绩后再谈切换或融合。

### 4.3 融合方向（同协议对决之后才有数据支撑）

- 点预测：两臂 P50 取中位数（对异常值稳健，通常优于单臂）；
- 区间：分位数平均或按历史 pinball 加权；
- 不做：MQ-CNN + MQ-RNN 互融（同族，多样性收益≈0）。

## 5. 同协议对决：已执行（2026-10-22）

协议：林的 15 任务日滚动重训口径（每个任务日只用其之前的数据训练，预测当日 24h，
评价集 = 15×24 = 360 个样本外点）。MQ-RNN 已移植主线
（`backend/app/domain/forecast/price_mqrnn.py`，架构与她的 product/ 版逐项对齐），
接入 `scripts/run_price_benchmark.py` 作为 `mqrnn` 臂。

数据说明：GEFCom2014-P 原始数据不在任何一侧仓库。本次使用公开镜像重建
（`data/power/price/Price/`，来源 unresponsive51/GEFCom2014Price），
**完整性已交叉验证**：与 July 测试存档的 3744 个逐点真值比对，最大偏差 0.0。
美东夏令时缺口（2013-03-10 02:00）单点前向填充，不影响任何任务日真实值。
官方 BenchmarkN_P 分位数文件缺失，`gefcom_benchmark` 臂本轮缺测
（docs/15 已证 naive_weekly 与其 14/15 任务日逐点一致，可近似代表）。

### 5.2 三个必须如实报告的结论

1. **MQ-CNN 旧数字（MAE 10.77 / +17.3%）是泄漏的产物，作废。** 原基准把全序列
   喂给 MQ-CNN 训练，任务日之后的未来数据参与了训练；截断修正后其真实水平是
   MAE 29.37 / skill −125.5%，比"上周同时刻"略好、远不如"昨日延续"。
   docs/15 §4.2/§4.3 已同步更正。这也反向验证了防泄漏测试的价值。
2. **July 的 MQ-RNN 在严格日前协议下输给昨日延续（−9.2%）**，她在自己协议下的
   +20.2% 与 81.4% 区间覆盖率不能外推到此协议。注意口径差异：本次为 calendar-only
   移植（忠于她的 GEFCom 适配），**没有用日前负荷预报**这个 GEFCom 协议内合法的
   未来协变量，而 LightGBM 用了——这是特征口径差异，不全是模型容量差异。
3. **分任务明细给出明确的下一步**：MQ-RNN 在普通日与 LightGBM 互有胜负
   （06-17 赢 26%、07-13 接近），在 07-20 尖峰日**全场最佳**（MAE 8.94 vs
   lgbm 10.73 vs naive 58.58），但在 07-18/07-19 热浪尖峰崩盘（45.9/48.2，
   偏差 −5.8 显示系统性低估尖峰）。热浪尖峰的第一驱动量正是温度→负荷，
   而模型拿不到负荷预报。**把日前负荷预报加进 MQ-RNN 的未来特征**是优先级
   最高的改进，改完再重跑本对决，才谈得上注册为第二生产臂或融合。

### 5.3 对组合方案的修正

docs/18 §4 的"MQ-RNN 重训后作第二臂"暂缓：当前 calendar-only 口径未达到
生产臂门槛（C4：skill > naive_daily）。修正后的路线：

1. MQ-RNN 补负荷协变量 → 重跑本对决 → skill 转正且峰值命中 ≥ 0.5 再谈注册；
2. 融合实验仍有依据（07-20 的互补性说明两臂误差相关性低），但排在第 1 步之后；
3. LightGBM 生产骨干地位经本次对决**加强**，不变。

## 6. 附：AMPDNet（July 10-20 上传的光伏深度模型）现状

与电价模型分开记录，避免混淆——这是**光伏功率**模型，不是电价模型。

- **交付完成度高**：Solar1/2/6/7/8 × 15min/1h/4h 共 15 个权重全部完成 20 轮训练
  （按验证集 MAE 选轮，非第 2 轮草稿），TorchScript 图 + 元数据 + 校验值齐全；
  `verification.json` 显示 113,695 个测试窗口、794,530 个预测点全部数值验证通过，
  TorchScript 与 eager 输出逐点一致（max diff = 0.0）。这份交付的工程严谨度很高。
- **但它不是插上就能用的**：
  - 输入是 TSI/DNI/GHI/温度共 4 通道的**白昼压缩采样**（06:00–18:45 每 15 分钟，
    夜间被压缩掉），不是历史功率；我们的站点没有 TSI（总天空成像）数据源；
  - 源站是 30–130 MW 的地面大站，与我们 1000 kWp 屋顶场景量级差两个数量级，
    manifest 明确"未验证跨站泛化、不支持跨容量缩放"；
  - 只输出同日白昼、**拒绝跨夜**——它是日内滚动修正模型，不是日前预测模型；
  - 上游训练库 pinned checkout 无 LICENSE，再分发许可未确认。
- **系统内定位**：若接入，对应光伏链路的"15 分钟~4 小时短临滚动修正"档位
  （docs/12 路线图中预留给天空相机/云图算法的位置），需用本站数据重训后
  经注册表登记为 opt-in 实验臂，**不替代默认物理链**。接入代码
  （`ampdnet.py`，输入校验写得相当严格）可从 product/ 树移植，但优先级低于
  电价同协议对决与 docs/17 主实验。
