# 光储一体 · 储能配置优化系统设计

> 目标：面向工商业用户，结合**光伏功率预测**与**电价预测**，输出**储能配置方案**与**日充放电策略**
> 版本：v0.1 设计稿　|　日期：2026-09-19

---

## 〇、设计前提（2026-09-19 已确认）

| 决策项 | 选定 | 架构影响 |
|---|---|---|
| **系统形态** | **规划 + 运行都做** | 两者共享同一个优化内核，只是时间尺度与决策变量不同 |
| **电价机制** | **峰谷分时为主，现货可切换/叠加** | 电价模块做成 **Provider 可插拔**——这是本节最重要的设计 |
| **用户类型** | **工商业用户** | 收益 = 峰谷套利 + 需量电费削减 |
| **目标地点** | **未定 → 全配置化** | 一切地域相关参数进配置文件，换地点不改代码 |

### 0.1 「规划 + 运行」共享优化内核

两种模式本质是**同一个优化问题**，只是时间尺度与决策变量不同：

| | 规划（Sizing） | 运行（Dispatch） |
|---|---|---|
| 触发 | 一次性 | 每日滚动 |
| 输入 | 站点参数 + 典型日 / 全年代理日 | 次日预测曲线 + 当前 SOC |
| **决策变量** | **容量 kWh / 功率 kW** + 每时段功率 | 仅每时段功率 |
| 目标 | 全生命周期 NPV 最大 | 当日电费最小 |
| 额外约束 | 投资预算、场地面积 | SOC 上下限、循环次数 |

**共同点：都是在约束下最小化电费。** 所以代码结构应该是：

```
optimizer/
├── core.py        目标函数 + 约束构造（两者共用）
├── sizing.py      规划：决策变量含容量
└── dispatch.py    运行：容量固定，只决策每时段功率
```

> 不要为两者各写一套优化逻辑——那会导致"规划说能回本、运行却赚不到"的口径不一致。

### 0.2 电价模块：Provider 可插拔 ⭐

需求是"基础用分时，当地开通现货后能切换或叠加"。**关键是让下游无感知**：

```
TariffProvider（抽象接口）
├── TouProvider          峰谷分时：读省级目录电价表
├── SpotProvider         电力现货：接市场接口 / 价格预测模型
└── CompositeProvider    叠加模式：现货价替代电能量部分
```

**统一出参**（无论哪种模式，优化器和前端看到的都一样）：

```python
class PricePoint:
    ts: datetime
    price: float            # 到户电价 元/kWh
    energy_price: float     # 电能量价格（可被现货替代的那部分）
    tier: str | None        # peak / flat / valley / sharp（现货模式下可为 None）
    p10: float | None       # 现货模式的价格区间下界
    p90: float | None       # 上界
```

#### ⚠️ "叠加"的准确含义（这里最容易搞错）

中国工商业**到户电价**的构成是：

```
到户电价 = 电能量价格 + 输配电价 + 政府性基金及附加
```

参与现货市场后，**只有「电能量价格」这一项被现货价替换**，输配电价和政府性基金仍按原规则执行。

所以"叠加"**不是两个价格相加**，而是：

```python
if mode == "tou":
    energy = tou_table.get(ts)          # 目录分时价
elif mode == "spot":
    energy = spot_price(ts)             # 现货价
elif mode == "tou_plus_spot":
    energy = spot_price(ts)             # 现货价替代电能量部分
    tier = tou_table.tier_of(ts)        # 时段标签仍保留，供 UI 画色块

price_to_customer = energy + transmission_and_fund
```

**把这个差异消化在 Provider 内部，优化器和前端一行都不用改**——这正是做成可插拔的意义。

### 0.4 光伏预测：按预见期路由 ⭐

**没有一种方法能覆盖全部预见期。** 三个时域各有强项，系统按预见期自动选择：

| 时域 | 方法 | 输入 | 实测水平 |
|---|---|---|---|
| **短临**（< 1 h） | 全天空图像 SUNSET | 天空图像 + 历史功率 | 晴天 **98.51%** / 阴天 89.52% |
| **超短期**（1~6 h，第 4 小时） | 近 N 天同刻均值 + 偏差延续 | **仅历史功率** | **95.06%** 达标 |
| **短期**（> 19 h，D+1 起 72 h） | 日周期气候态 + 气象预报 | NWP 预报 | 待实现 |

> 分界点依据：Bacher 等 (2009) 实测——**预见期超过 19 小时，加入实测功率仅带来 1% 改善**，
> 所以长时域必须靠气象预报，而不是历史功率。

#### ⚠️ 关于「老师给的全天空图像算法」的定位

这是个需要说清楚的问题：**系统主链路用统计法，不代表图像算法没用。**

**① 图像算法的适用范围就是短临，这由物理本质决定。**

天空图像能看到「云现在在哪、往哪飘」，据此外推 15~60 分钟很有效。
但**云的生消（生成与消散）无法从图像外推**——4 小时后天上的云与现在没有必然联系。
实测印证：论文自报的 SUNSET Forecast skill 在**晴天为 −45.8%**
（即打不过"用当前值"这个笨办法），只有阴天 +17.0%。

**② 它在本项目里是核心成果，不是边角料。**

官方基准上完成 10 折复现，**三项指标全面优于原论文**：

| 分组 | 复现 RMSE | 论文 RMSE | 改善 |
|---|---|---|---|
| 晴天 | **0.4477** | 0.80 | ↓ 44.0% |
| 阴天 | **3.1547** | 3.34 | ↓ 5.5% |
| 整体 | **2.2554** | 2.43 | ↓ 7.2% |

这是报告「实验验证与结果」（25 分）里最硬的材料之一，也是"不只是会调参"的证据。

**③ 系统里保留它的位置，做成可选增强。**

```
             ┌─ 有全天空相机 → SUNSET 图像模型（短临精度最高）
光伏功率预测 ─┤
             └─ 无相机       → 持续性 / 统计法兜底（同样可用）
```

大型地面电站**确实有配全天空相机的场景**（云观测、气象服务），
所以这不是为应付而留的接口，而是**真实的产品分层**：
客户有硬件就启用增强，没有就用统计法，两条路都能交付。

**该淘汰的是「不分场景一律用图像」，不是图像本身。**
正确划定方法的适用边界比在每个场景硬用更专业——评审看的是判断力，不是使用痕迹。

## 一、系统边界

```
┌─────────────────────────────────────────────────────────────┐
│                        系统负责                              │
│  光伏功率预测 → 负荷预测 → 电价预测 → 储能容量配置 → 日调度   │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                      系统不负责（明确划出）                    │
│  · 储能设备的电气设计与安全认证                                │
│  · 电力交易申报（只出建议，不代报）                             │
│  · 实际 EMS 的实时控制（输出计划，由现场 EMS 执行）             │
└─────────────────────────────────────────────────────────────┘
```

**边界清晰很重要**——给企业讲方案时，"我们不做什么"往往比"我们做什么"更能建立信任。

> ⚠️ **地点字段决定了三件事**，所以绝不能省：
> ① 光伏资源（辐照度）→ 决定气象数据源与理论发电量
> ② 电价政策（省级目录电价）→ 决定收益模型
> ③ 气候特征（梅雨/雾霾/积雪）→ 决定预测模型的适用性

### 2.2 三类输入数据

| 数据类型 | 来源 | 获取方式 | 更新频率 |
|---|---|---|---|
| **气象预报** | Open-Meteo（免费）/ 和风天气 / 中国气象局 | 系统**自动拉取**，按经纬度 | 每小时 |
| **电价** | 省级目录电价（人工录入模板）+ 现货（若有） | 模板一次录入，长期复用 | 政策调整时 |
| **历史运行** | 用户 SCADA / 逆变器 / 电表导出 | 用户上传 CSV，或 API 对接 | 每日增量 |

## 三、接口设计 ⭐（你最关心的部分）

### 3.1 统一约定（先立规矩，后面所有接口都遵守）

| 项 | 约定 | 理由 |
|---|---|---|
| 协议 | REST + JSON，UTF-8 | 通用 |
| 时间戳 | **ISO 8601 带时区**，如 `2026-09-19T08:00:00+08:00` | 避免跨时区歧义 |
| 时间序列 | 统一 `points` 数组，不用宽表 | 变长序列好处理 |
| 单位 | **写在字段名里**（`capacity_kwp`、`power_kw`） | 避免 kW/kWp/kWh 混淆——这是能源行业最常见的错误 |
| 缺失值 | `null`，**绝不用 0 代替** | 0 是有效值（夜间功率就是 0） |
| 精度 | 功率 0.1 kW，电价 0.001 元，SOC 0.001 | 够用且省体积 |

### 3.2 接口清单

| # | 路径 | 方法 | 用途 | 谁调用 |
|---|---|---|---|---|
| 1 | `/api/v1/sites` | POST / GET | 建站、查站点 | 前端 |
| 2 | `/api/v1/sites/{id}` | GET / PATCH | 站点详情、改参数 | 前端 |
| 3 | `/api/v1/sites/{id}/measurements` | POST | **上传实测**（光伏、负荷） | 用户/SCADA |
| 4 | `/api/v1/sites/{id}/weather` | GET | **拉取气象预报**（系统自动） | 内部 |
| 5 | `/api/v1/tariffs` | POST / GET | 电价模板管理 | 运营 |
| 6 | `/api/v1/forecast` | POST | **统一预测入口**（三种目标） | 前端 |
| 7 | `/api/v1/storage/sizing` | POST | **容量配置计算** | 前端 |
| 8 | `/api/v1/storage/schedule` | POST | **日调度计划** | 前端/EMS |
| 9 | `/api/v1/reports/{id}` | GET | 导出方案报告 PDF | 前端 |

### 3.3 能获取什么数据 —— 逐接口说明

#### ① 气象预报 `GET /sites/{id}/weather`

系统根据站点经纬度**自动拉取**，用户不需要做什么。

```json
{
  "site_id": "S001",
  "source": "open-meteo",
  "fetched_at": "2026-09-19T06:00:00+08:00",
  "resolution_minutes": 60,
  "horizon_hours": 72,
  "variables": [
    "shortwave_radiation", "direct_normal_irradiance", "diffuse_radiation",
    "temperature_2m", "cloud_cover", "relative_humidity", "wind_speed_10m"
  ],
  "points": [
    {
      "ts": "2026-09-19T07:00:00+08:00",
      "shortwave_radiation": 128.0,
      "temperature_2m": 24.3,
      "cloud_cover": 35
    }
  ]
}
```

**关键**：`shortwave_radiation`（短波辐射）就是光伏预测的核心输入——**相当于 GEFCom2014 里的 NWP 变量**。

#### ② 实测数据上传 `POST /sites/{id}/measurements`

```json
{
  "data_type": "pv_power",
  "unit": "kW",
  "resolution_minutes": 15,
  "points": [
    {"ts": "2026-09-18T00:00:00+08:00", "value": 0.0},
    {"ts": "2026-09-18T12:00:00+08:00", "value": 623.4}
  ]
}
```

允许的 `data_type`：`pv_power` / `load_power` / `storage_soc` / `grid_power`

#### ③ 统一预测 `POST /forecast` ⭐ 核心接口

**一次请求可以要三种预测**：

```json
{
  "site_id": "S001",
  "targets": ["pv_power", "load_power", "price"],
  "horizon_hours": 72,
  "resolution_minutes": 15,
  "issued_at": "2026-09-19T06:00:00+08:00",
  "options": {
    "include_uncertainty": true,
    "quantiles": [0.1, 0.5, 0.9]
  }
}
```

**返回格式**（这是整个系统的数据契约，要设计得经得起推敲）：

```json
{
  "site_id": "S001",
  "issued_at": "2026-09-19T06:00:00+08:00",
  "horizon_hours": 72,
  "resolution_minutes": 15,
  "forecasts": [
    {
      "target": "pv_power",
      "unit": "kW",
      "model": {"name": "SUNSET-hybrid", "version": "1.0"},
      "accuracy": {
        "metric": "1 - RMSE/Cap",
        "value": 0.9251,
        "caliber": {
          "normalization": "rated_capacity",
          "cap_kw": 1000,
          "includes_nighttime": false,
          "spatial_scale": "single_site",
          "baseline": "persistence"
        }
      },
      "points": [
        {"ts": "2026-09-19T07:00:00+08:00", "value": 12.4, "p10": 8.1, "p90": 18.9},
        {"ts": "2026-09-19T12:00:00+08:00", "value": 612.8, "p10": 420.0, "p90": 780.2}
      ]
    },
    {
      "target": "price",
      "unit": "CNY/kWh",
      "model": {"name": "TOU-direct", "version": "1.0"},
      "accuracy": {"metric": "n/a", "note": "分时电价为政策给定，无需预测"},
      "points": [
        {"ts": "2026-09-19T07:00:00+08:00", "value": 0.5583, "tier": "flat"}
      ]
    }
  ]
}
```

**三个设计要点，建议保留**：

1. **`accuracy.caliber` 字段** —— 把精度口径随结果一起返回。
   这是我们从三个数据集的分析里学到的：**没有口径的精度数字等于没有信息**。
   企业客户拿到 92.51% 会问"含不含夜间"，接口直接回答。

2. **`p10/p90` 分位数字段** —— 给储能策略提供风险边界。
   乐观情景用 p90（多充电）、悲观用 p10（保底）。
   这是 FQRA（分位数回归平均）那篇论文的直接价值。

3. **`accuracy.note`** —— 分时电价是政策给定，**根本不需要"预测"**，
   接口要如实说明，不能假装做了个模型。这一点在答辩时是加分项。

## 四、曲线展示设计 ⭐（你问的"怎么展示给用户看"）

### 4.1 主视图：三层同步时间轴

```
        00:00    04:00    08:00    12:00    16:00    20:00    24:00
           │        │        │        │        │        │        │
① 电价  ┌──┬────────┬────────┬────────┬────────┬────────┬──┐
  阶梯图 │谷│  平段  │  高峰  │  尖峰  │  高峰  │  平段  │谷│   ← 背景色块标档位
        └──┴────────┴────────┴────────┴────────┴────────┴──┘
           │        │        │        │        │        │        │
② 功率   │        ╱▔▔▔▔▔▔▔▔▔╲        │        │        │        │  ← 光伏（面积图）
  曲线   │    ___╱            ╲___    │        │        │        │
        ─┴────────────────────────────┴────────┴────────┴────────┴─ ← 负荷（折线）
         ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ ← 净负荷（虚线）
           │        │        │        │        │        │        │
③ 储能  ┌──────┐        ┌────────┐        ┌──────┐          ┌──┐
  动作带 │ 充电 │        │  放电  │        │ 充电 │          │放│
        └──────┘        └────────┘        └──────┘          └──┘
                              SOC ┄┄┄╱▔▔▔╲┄┄┄┄┄┄╱▔▔▔╲┄┄
```

### 4.2 六条展示规范（都是踩过坑的经验）

**① 电价必须用「阶梯图」，不能用折线图。**

中国峰谷分时电价是**时段制**：`08:00-11:00` 固定 1.2 元，`11:00` 整点跳到 0.8 元。
用折线图会画出斜线，让用户误以为电价是连续渐变的。
**这是国内能源看板最常见的错误**，改对之后专业感立刻不一样。

ECharts 里对应 `series.type = 'line'` + `step: 'end'`。

**② 电价档位用背景色块标注**（markArea）

| 档位 | 颜色 | 含义 |
|---|---|---|
| 尖峰 | 深红 | 最贵，储能必须放电 |
| 高峰 | 橙 | 贵，优先放电 |
| 平段 | 灰 | 中性 |
| 低谷 | 绿 | 最便宜，储能必须充电 |

用户一眼就能看到"什么时候该动作"。

**③ 光伏用面积图，负荷用折线。**

- 光伏 = **发电量**，面积填充有"能量累积"感
- 负荷 = **需求量**，折线更清晰

两者视觉形态不同，用户不会混淆。

**④ 净负荷曲线是全图的灵魂。**

```
净负荷 = 负荷 − 光伏
```

这就是"**需要从电网买多少电**"——储能的削峰填谷削的就是它。
建议用虚线画，并在下方用浅色填充标出"正/负"区域。

**⑤ 储能动作用正负条形带。**

- 0 轴以上 = 充电（从光伏余电或谷电取电）
- 0 轴以下 = 放电（供负荷，减少买电）

配色建议：**充电用蓝（吸收），放电用绿（释放）**。

**⑥ SOC 曲线必须叠加。**

用户最关心的永远是"**电池还剩多少电**"。SOC 曲线用细虚线叠在储能动作带上，
一眼看出"有没有放空"或"充不满"。

### 4.3 三个视图层级（不要一屏塞满）

| 视图 | 内容 | 面向谁 |
|---|---|---|
| **总览** | 今日收益、SOC、当前动作、明日计划 | 企业主 / 运维 |
| **曲线** | 上面那三层图（可切 24h / 72h / 月度） | 运维 / 能源经理 |
| **方案** | 容量配置、投资测算、回本周期、敏感性分析 | 决策层 |

### 5.3 优化模型（从简到繁，三档）

| 档位 | 方法 | 复杂度 | 状态 |
|---|---|---|---|
| **一档** | **规则式**：谷时充、峰时放，按 SOC 上下限截断，**含削峰优先与电量预留** | 极低 | ✅ **已实现**（`src/optimizer/dispatch.py`） |
| 二档 | **线性规划（LP）**：目标函数 = 电费最小化，约束 = SOC/功率/循环次数/需量 | 中 | ⏳ 待做 |
| 三档 | **随机优化 / 鲁棒优化**：用 p10-p90 区间处理预测不确定性 | 高 | ⏳ 有余力再做 |

**一档已能出可用结论**——峰谷时段已知，规则式天然接近最优。
实测示例站点（1 MWp 光伏 / 1800 kW 负荷峰值）的推荐配置为
**550 kW / 1100 kWh**，回收期 4.25 年、IRR 19.8%（合成数据，仅验证链路）。

#### ⚠️ 一档踩过的两个坑（值得写进报告）

**坑一：只按电价时段充放，会把需量电费越充越高。**

谷时满功率充电，充电负荷叠加在夜间负荷上，把并网峰值从 542 kW 推到 706 kW，
月基本电费反而多缴 6,235 元——省下的电度电费从这里加倍还回去。

**坑二：只按电价时段放电，中午就把电放空了。**

实测某站点在 13:00-16:00（光伏还在发电、净负荷仅 50~380 kW）就把 SOC
从 95% 放到 17%，等 18:00-19:00 净负荷升到 650~684 kW 的真实峰值时已无电可放。
**结果是削峰量为 0，需量电费一分钱没省。**

修复方式是在调度里显式引入**削峰目标**（`peak_target_kw`）：

```
① 充电功率不超过目标（而不是基线峰值）
② 放电分两种情形：
   净负荷已超目标 → 无条件放电削峰（不看电价时段）
   未超目标但处于峰段 → 套利放电，但扣除「后续削峰所需电量」
```

修复后同一站点的四种策略对比：

| 方案 | 并网峰值 | 基本电费/月 | 电度电费/日 |
|---|---|---|---|
| ① 不配储能（基线） | 542.1 kW | 20,601 元 | 4,661.8 元 |
| ② 储能·忽略需量 | **706.2 kW** | **26,836 元** | 4,464.8 元 |
| ③ 储能·仅需量感知 | 542.1 kW | 20,601 元 | 4,376.7 元 |
| ④ 储能·主动削峰 80% | **433.7 kW** | **16,481 元** | **4,332.6 元** |

**② 是反面教材，③ 只是「不让情况恶化」，④ 才把储能的双重价值都拿到。**

> 这两个坑 LP 版本能自然规避（把需量写进目标函数），
> 但修复过程本身是很好的报告素材——**说明团队不是"能算"，而是"算得对"**。
>
> 削峰目标取多少不是拍脑袋定的，而是 **sizing 的决策变量之一**：
> 目标越低，需量电费省得越多，但谷时充电余量越小、套利收益下降。
> 见 `src/optimizer/sizing.py` 的 `DEFAULT_SHAVING_RATIOS`。
